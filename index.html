Open .agents Standard

A production-ready foundation for portable agents.

The Open .agents Standard aims to make agent definitions easier to share, inspect, version, and run across tools and platforms.

Instead of treating every harness as a one-off integration, the standard proposes a canonical .agents/ project structure that can be translated into the ad-hoc configuration formats used by existing agent runtimes today.

Explore the proposed structure View the repository

Why it matters

Agents become more useful when they are interoperable. An open standard can reduce lock-in and help teams move definitions between ecosystems.

Core goals

  • Portable agent definitions
  • Readable, versionable specifications
  • Open collaboration across tools and communities
  • A canonical model that can compile down to current harnesses

Design principle

Author agents once in a stable open structure, then translate them into runtime-specific prompts, tool manifests, metadata files, or workflow descriptors as needed.

Important aspects of the standard

A useful open agent standard needs to cover more than prompts. It should describe identity, instructions, tools, knowledge, policies, execution profiles, and compatibility layers for current ecosystems.

  • Canonical agent metadata
  • Portable system instructions
  • Tool and capability declarations
  • Knowledge and attached assets
  • Execution profiles and policies
  • Harness translation targets

Current status

The standard is emerging, but the authoring model can still be production-ready if it focuses on stability at the canonical layer and allows harness-specific adapters to evolve independently.

Stable authoring surface

Agent authors work in one canonical tree instead of re-writing the same intent in several incompatible formats.

Adapter-based interoperability

Translators can target current harnesses without forcing those harnesses to adopt the same internal configuration model.

Incremental adoption

Teams can introduce .agents/ alongside existing runtime configs, then automate generation over time.

Proposed .agents directory structure

The proposed layout below keeps authoring concerns separate while giving translators enough structure to generate harness-specific configuration files automatically. 

.agents/
  agent.yaml                # canonical metadata: name, description, version
  instructions.md           # primary system instructions for the agent
  tools/
    github.yaml             # tool declarations, permissions, and policies
    web.yaml
  knowledge/
    product-overview.md     # reusable reference material
    glossary.md
  profiles/
    default.yaml            # default model/runtime settings
    reviewer.yaml           # alternate persona or execution profile
  workflows/
    triage.yaml             # reusable task entry points
  harnesses/
    copilot.yaml            # output target options and field mappings
    claude-code.yaml
    openai.yaml

How the canonical structure maps to existing harnesses

The standard does not require existing tools to change overnight. It can act as a source format that translates into the custom files and fields each harness already expects.

.agents concept Canonical source Typical harness output Translation intent
Agent identity .agents/agent.yaml Name, description, labels, runtime metadata Preserve stable agent identity across platforms.
System instructions .agents/instructions.md Prompt files, instruction blocks, assistant bootstrap text Keep one source of truth for core behavior.
Tool permissions .agents/tools/*.yaml Allowed tools lists, function manifests, MCP/tool schemas Map capabilities into each harness permission model.
Knowledge assets .agents/knowledge/* Attached files, retrieval sources, context bundles Reuse the same reference material without duplication.
Execution profiles .agents/profiles/*.yaml Model presets, reasoning levels, temperature/runtime knobs Adapt one agent to multiple operating modes safely.
Harness adapters .agents/harnesses/*.yaml Per-platform overrides and target-specific field mappings Handle gaps where a harness has bespoke configuration.

Translation model

In practice, a translator or build step can read the canonical .agents/ tree and emit the format required by a given harness. The goal is not to erase differences, but to isolate them in a clear adapter layer. 

canonical .agents/ definition
        ├── shared metadata
        ├── shared instructions
        ├── shared tools and knowledge
        └── target-specific adapter rules
                ↓
      generated harness config
        ├── prompt/instruction file
        ├── tool manifest or allowlist
        ├── model/runtime settings
        └── optional workflow/task wrapper

Concrete translation example

The canonical definition should be specific enough to generate real runtime assets, while still remaining human-readable and easy to review.

Canonical source

agent:
  name: reviewer
  description: Reviews changes for correctness
instructions: instructions.md
tools:
  - github
  - bash
profile: reviewer

Harness output

name: reviewer
system_prompt: ./instructions.md
allowed_tools:
  - github
  - bash
runtime:
  profile: reviewer

Adoption path

A practical rollout path should improve portability immediately, without blocking teams on a finalized specification or a single reference implementation.

  1. Author the agent once in .agents/.
  2. Keep the canonical instructions, tools, and profiles under version control.
  3. Generate or sync harness-specific configurations from the canonical source.
  4. Validate runtime behavior in the target harnesses.
  5. Refine the shared schema only when multiple harnesses need the same concept.

Specification priorities

Portability first

Definitions should survive moves across repositories, vendors, and orchestration environments with minimal rewriting.

Explicit capability boundaries

Tool permissions, policies, and execution profiles should be declared clearly enough to support review and governance.

Readable by humans

The source format should be optimized for authoring, code review, and long-term maintenance, not just machine generation.
